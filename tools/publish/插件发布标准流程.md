# 插件发布标准流程（自 v1.2.0 起生效 · v2.5.2 增设发布门禁）

> **工具位置**：本文件与 `sync-publish.mjs` / `check-release.mjs` / `update-plugin.mjs` 现在**随仓库走**
> （`DSH/tools/publish/`），不再散落在某台机器的 `dist/publish/` 里 —— 换机器、换工作区都不会丢。
> **路径解析**：`paths.mjs` 按「环境变量 → `config.local.json` → 默认值」取副本根目录 / 插件源目录 /
> DSH profile 目录。换机器时复制 `config.example.json` 为 `config.local.json` 改路径即可，**脚本一行都不用改**。

> 适用插件：`dsh-weekly-report-lau`（周报工作台）、`dsh-session-index-lau`（会话索引）、`dsh-siyuan-bridge`（思源桥）
> 铁律 1：**所有插件更新一律走「仓库 → npm → 安装更新」三段式，禁止手工改 profile node_modules 副本**（pnpm 重装会按 registry 还原，手改必被冲掉，且曾因整文件覆盖破坏 `-lau` 改名导致 DSH 校验失败）。
> 铁律 2：**任何改动必须先通过发布前核验门禁，确认版本可用，才允许推进 ⑤→⑨**。核验未通过时禁止发布、禁止跳过、禁止「先发再修」。
> 铁律 3：**保持版本统一**——「源仓库 / 发布副本 / npm latest / DSH 已装」四处版本号必须相同，且关键脚本内容必须一致。同版本号但内容不同视为不统一，必须走完整流程补齐。

## 流程总览

```
① 源目录开发/修复 → 功能核验（check + smoke + 新流程自检）
        ↓
② 版本号递增（小改动末位 / 功能级第二位 / 不兼容首位）→ 全仓版本声明同步
        ↓
③ 仓库代码更新并推送（公库本地常驻；私库按需临时 clone → 推送 → 删除）
        ↓
④ 同步 npm 发布副本：node sync-publish.mjs <key>   ← 本地可回滚，先备齐再核验
        ↓
④.5 【门禁】node check-release.mjs <key> --pre   ← 未全绿禁止 ⑤ 发布
        ↓
⑤ 发布：npm publish --access public（发布副本目录内）
        ↓
⑥ 等 staged publishing 生效（实测 1~8 分钟）→ npm view <包名> version 确认
        ↓
⑦ 更新安装：DSH profile 目录 pnpm update <包名>@<新版本>（先登记供应链豁免）
        ↓
⑧ 【门禁】node check-release.mjs <key> --post  → 四处统一 + MCP 握手
        ↓
⑨ 完全退出 DSH 再打开，确认插件页加载新版
```

## 各段操作细节

### ① 源目录（唯一开发现场）
- 周报：`D:\WorkBuddy工作区\Tool开发\dsh-weekly-report`
- 会话索引：`D:\WorkBuddy工作区\Tool开发\DSH`
- 思源桥：`D:\WorkBuddy工作区\Tool开发\dsh-siyuan-bridge`
- 改动必须 `npm run check` + `npm run smoke` 全绿，且**新增功能各自跑通一次功能核验**（例如批量推送跑只读预览、MCP 新工具跑握手探测）后才进入下一环节。
- 版本号递增后，必须同步 `package.json` / `plugin.json` / `server.mjs VERSION` / `smoke.mjs` 断言 / `README.md` / `操作使用手册.html` 六处；门禁会逐一核对，漏一处直接 FAIL。
- 源目录 `package.json` 保留 `"private": true`（防误在源目录 publish），发布化只发生在发布副本。

### ④.5 发布核验门禁（强制，发布前最后一道闸）

> 顺序说明：④ 同步副本是**本地可回滚**操作，必须先做完，门禁才能核验「源 + 副本 + registry」是否全部就绪；核验通过后 ⑤ 才是第一个不可逆动作。`--pre` 检查副本内容，所以不能排在 ④ 之前。

```bash
cd "D:\WorkBuddy工作区\Tool开发\DSH\tools\publish"
node check-release.mjs session-index --pre      # --post 用于安装后
node check-release.mjs siyuan-bridge --pre     # 面板类：通用检查，无 MCP 握手
```

`--pre` 检查（任一 FAIL 即退出码 1）：

| 项 | 内容 |
|---|---|
| 版本声明一致 | 源仓库六处版本串全部相同 |
| 工作区干净 | `git status --porcelain` 为空，禁止发布未提交改动 |
| 语法 / 冒烟 | 全量 `node --check` + `smoke.mjs` 全绿（会话索引 86 项 / 思源桥 38 项，含标准形态断言） |
| 功能核验 | 批量推送脚本只读预览可跑通 |
| 新流程标志 | 持久化判重 / `--seed` / 丢弃不重推三项都在 |
| 发布副本 | `sync-publish.mjs --check` 自检通过、版本一致、无 legacy 安装器残留 |
| registry | 目标版本尚未发布（同版本必被拒） |

`--post` 检查：npm latest / 发布副本 / DSH 已装 / 源仓库四处版本一致；副本与已装包的批量脚本行为一致、运行时文件齐全；`cordis.patch.yml` 挂载名、`server-path.txt` 指向；**直接启动已装包做 MCP 握手**（版本、14 工具、`stage` 探测思源桥）。

> `--fast` 会跳过冒烟，仅用于调试脚本本身，**不得作为放行依据**。

### ③ 仓库同步
- **会话索引**：源目录 `Tool开发/DSH` 本身就是 git 仓库，`git push origin main`（`Lau-Jin/DSH`）即完成；私库/公库不含该插件。
- **公库（本地常驻）**：`D:\Lau-tool-public` → `Lau-Jin/dsh-weekly-report`，脱敏版；同步 `dsh-weekly-report/` 子目录后 `git add dsh-weekly-report/ && git commit && git push origin main`，提交前确认无个人姓名、真实学校、真实工单链接。
- **私库（本地检出已删除，2026-11-14 起按需临时 clone）**：`Lau-Jin/Lau-tool` 仍保留在 GitHub，本机不再常驻。需要同步时：
  ```bash
  TMP=$(mktemp -d)/Lau-tool
  git clone --depth 1 git@github.com:Lau-Jin/Lau-tool.git "$TMP"
  # 把源目录的 dsh-weekly-report/ 同步进 "$TMP/dsh-weekly-report/"（node_modules / .cache 不入库）
  cd "$TMP" && git add dsh-weekly-report/ && git commit -m "..." && git push origin main
  # 推完即可删除临时目录
  ```
  只 `git add dsh-weekly-report/`，**不要 `git add -A`**（私库有其它项目目录）。
- **注意**：原 `D:\Lau-tool` 里 3 个未入库的本地插件已迁到 `D:\DSH本地插件\`，DSH profile 的 3 条 `link:` 已改指新位置；不要在临时 clone 里找它们。

### ④ 发布副本同步（脚本自动完成，禁止手工覆盖）
```bash
cd "D:\WorkBuddy工作区\Tool开发\DSH\tools\publish"
node sync-publish.mjs weekly-report    # 或 session-index / siyuan-bridge
# 同步会删除副本里源目录已不存在的文件（含 docs/、dist/ 等排除目录内的残留）
```
脚本自动完成并校验：
- 源目录 38+ 文件同步到 `<副本根>/<npm包名>/`，删除源目录已不存在的文件
- **包名改名**（`-lau` 后缀，仅改名单内文件，URL 不受影响）
- package.json 发布化：去 private、`engines.dsh`、`publishConfig.access=public`
- 校验（任一失败即中止）：挂载名==包名（bundleMatch）、旧包名残留 0、打包清单无 `.cache`/`config.json`/`node_modules`、敏感内容扫描、registry 版本不重复
- **④ 必须重新执行，不能只改版本号**：`sync-publish.mjs` 是唯一把源目录内容带进副本的通道。只改版本号而不重跑，会造成「同版本号、内容不同」的分叉（见历史事故表）。
- 新增目录（如 `tools/`）要同时加进源目录 `package.json` 的 `files` 白名单，否则 npm 包会漏文件。

### ⑤⑥ 发布与生效
```bash
cd "<副本根>/<npm包名>"
npm publish --access public
```
- 凭据：`C:\Users\Administrator\.npmrc` 内 lau-jin 的 Granular Access Token（Read and write + bypass 2FA）。
- 注意 npm **staged publishing**：发布后 registry 先出现 `0.0.0-stage` 占位，真实版本 3~8 分钟后才可安装；期间安装报 notarget/E404 属正常，用 `npm view <包名> version --prefer-online` 轮询。
- 该 token 不能 unpublish；`0.0.0-stage` 留在版本列表属正常痕迹。

### ⑦⑧ 更新安装（DSH profile）
```bash
cd "C:\Users\Administrator\.dsh\profiles\desktop"
npx -y pnpm@11.28.5 update dsh-weekly-report-lau
```
- 三个包已在 profile `pnpm-workspace.yaml` 的 `minimumReleaseAgeExclude` 中，**每个新版本必须先把 `包名@精确版本` 登记进去**，否则供应链冷却期会让 pnpm 静默回退旧版。
- profile 依赖保持 semver（如 `^2.5.2`），`update` 自动取满足范围的最新版；需要跨大版本时改写依赖再 `install`。
- 更新后必须跑 `node check-release.mjs <key> --post`，全绿才算发布完成；FAIL 时按输出定位，不要手工改 node_modules 兜底。
- 面板类插件（周报）遇到 `ERR_PNPM_EPERM` 目录锁时，改用 `node update-plugin.mjs <key> --version <版本>`（占位应答器 + 杀面板解目录锁）；会话索引/思源桥通常不需要。

## 新机制同步清单（会话索引插件）

这些能力随代码一起发布，改动时必须在 `--pre` 里保持可用：

| 能力 | 落点 | 核验方式 |
|---|---|---|
| 批量推送 WorkBuddy 会话文档 | `tools/push-doc.mjs --from-workbuddy` | 只读预览能列出清单 |
| 持久化判重（丢弃不重推） | `~/.dsh/session-index/push-doc-state.json` | 脚本含 `push-doc-state.json` / `--seed` / 「丢弃也不重推」 |
| 首次启用补种基线 | `--seed`（纯本地、不投递） | 状态文件条数与文档数一致 |
| 定时自动化 | 每小时任务 `d455a621…`，cwds 指向源仓库 | 自动化状态 ACTIVE；prompt 禁止 commit / 禁止 --force / 禁止删状态文件 |
| MCP 第 14 个工具 | `session_index_stage`（`lib/stage.mjs`） | `--post` 的 MCP 握手检查 14 工具 + 思源桥探测 |

注意：**定时自动化跑的是源仓库目录的脚本**，不是 npm 包里的副本。因此源仓库改动即使当时不发版也会对自动化生效——这正好是「同号不同内容」分叉的高发处，必须用 `--pre/--post` 把两边拉齐。

## 版本统一矩阵

| 位置 | 检查内容 |
|---|---|
| 源仓库 `DSH/package.json` | 版本号 + 六处声明一致 + 工作区干净 |
| 发布副本 `<副本根>/dsh-session-index-lau` | 版本号 = 源；关键脚本含新机制标志；打包清单完整 |
| npm `dist-tags.latest` | = 源版本；tarball 含 `tools/` 与 `lib/stage.mjs` |
| DSH `profiles/desktop/node_modules/dsh-session-index-lau` | 版本号 = 源；bundle 挂载名、`server-path.txt`、MCP 握手 |

**判定标准：版本号相同 + 关键文件内容/行为一致**，二者缺一不可。发现分叉时，正确做法是按 ②→④→④.5→⑧ 走完整流程发一个补丁版本，而不是手工同步文件或跳过发布。

## 纯 npm 包形态（v1.3.0 / v2.5.3 / v0.6.3 起）

三个插件均已移除「本地 link 安装 + 一键安装器 + 旧宿主兼容转发」体系，回归纯 npm 包形态：

- **不再随包分发**：`install.mjs`、`install.cmd` / `install.sh`、`update.cmd` / `update.sh`、`一键安装.vbs` / `.cmd` / `.command`、`docs/`。
  `package.json` 去掉 `setup` / `verify` / `uninstall` / `dry-run` 脚本，`files` 改精确白名单；
  `plugin.json` 删除 `automatic` 下的旧安装键与「手工安装」方式，`rollback` 统一为 `pnpm remove`。
- **保留的功能脚本**（非安装器，勿误删）：会话索引 `build-index.mjs` / `pack.mjs` / `lib/pack.mjs`；
  思源桥 `setup.mjs`（首次运行生成 `service/config.json`）、`start.sh` / `start.cmd`（手动起服务）。
- **安装 / 升级 / 卸载**统一走 `pnpm add` / `pnpm update` / `pnpm remove`，bundle 由 `cordis.patch.yml` 自动挂载。
- 两个插件的 `smoke.mjs` 均内置标准形态断言（无安装器残留、无 legacy 键、版本六处一致），防止回潮。
- **目录锁**：思源桥服务常驻 5599 会锁住 `node_modules` 目录，`pnpm update` 报 `ERR_PNPM_EPERM` 时改用
  `node update-plugin.mjs siyuan-bridge --port 5599 --version <版本>`（占位应答器接管心跳 → 解目录锁 → 更新 → 自动复活）。
  周报面板用默认 8798；工具通过 `--port` / `--probe` 适配两种心跳。

## 历史事故与规避（为什么必须走本流程）

| 事故 | 根因 | 本流程的规避 |
|---|---|---|
| DSH 显示周报插件未安装（2026-11-14） | 手工把仓库版 package.json/plugin.json 整文件覆盖进 npm 副本，`name` 被改回旧名，与注册的 `-lau` 冲突 | ④ 由脚本改名，且校验「挂载名==包名」「旧包名残留 0」 |
| npm 包险些带出真实数据 | v1.1.3 打包清单曾含 48 个 `.cache` 真实工单缓存（拦截）；v1.2.0 手册又发现真实学校名 | ④ 打包清单扫描 + 敏感内容扫描（同步时自动跑） |
| pnpm 重装后插件回退旧版 | 手改 node_modules 副本不是持久安装 | ⑦ 只通过 pnpm 从 registry 更新 |
| 同版本号但内容分叉（2026-11-14，v2.5.1） | 源仓库把批量判重改成持久化状态后未发版，npm 包与 DSH 已装仍是旧脚本；自动化跑源目录，行为与已装包不一致 | ④.5 门禁检查「发布副本含新流程脚本」+「registry 目标版本未发布」；强制走 ②→④→④.5→⑧ 发补丁版本拉齐四处 |
| npm 包漏带 `tools/` | 源目录 `files` 白名单没加新目录 | ④ 同步后检查打包清单，门禁核对副本含新流程脚本 |
