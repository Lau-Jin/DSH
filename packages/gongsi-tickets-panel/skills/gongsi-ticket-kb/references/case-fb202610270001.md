## 8. 完整走查示例：FB202610270001（真实案例，2026-10-29~30）

> 这一节是**照抄一次真实排查**得出的。把每个 Step 的**实际调用、实际返回、实际踩的坑**都记下来了，
> 照着这个骨架走就行。

### 8.0 场景

| 项 | 值 |
|---|---|
| 工单 | FB202610270001「学生信息同步失败问题分析」 |
| 处理人 / 状态 | 宋朋 / `assigned` |
| taskId | **993**（工单 `id` = **102**，两个数不同） |
| 工单描述全文 | 「冯主任运维群反馈学生学校同步失败」—— **就这一句** |
| 附件 | **0 个** |
| 工时 | `totalHours: 0`，任务上 0 条记录 |
| 补充材料 | 用户在对话中给了 `同步失败数据20261029154401.xlsx`（导出 2026-10-29 15:44:01） |

**这就是 Step 2 说的"描述过简"典型**：光靠工单字段根本没法拼检索词。

### 8.1 Step 1-2 — 取工单

关联任务 `task_get_task_detail(taskId=993)` → `status=新建`, `progress=0`, `dueTime=2026-11-03 18:00:00`。

### 8.2 Step 2 — 从补充材料里挖"事实"

解析 xlsx（openpyxl 读表头在第 2 行），得到：

```
失败 96 条 / 82 个班级
错误 100% 同一类："学生身上的班级信息在班级列表中无法查询到…"
抛出点 com.jeeplus.modules.manager.syn.service.UUserInfoService.saveStudent:207
payload 批次时间戳 2026-10-29 14:44:33 ~ 14:58:37   ← 说明是"今天刚跑的同步"
CLASSCODE 27 位 = COLLEGECODE(8) + MAJORCODE尾部(8) + 班级代码(11)
```

**这一步产出了 4 个检索关键词**：`班级列表中无法查询到`、`saveStudent`、`edu_class_info` / `class_info`、`同步学生班级数据`。
工单本身一个字都给不了，全靠这一步。

### 8.3 Step 3 — 检索词拆解与效果对比

**❌ 错误做法**：拿整段描述去搜
```
kb_search("统一身份认证 学生同步失败 班级 排查")   → 最高 0.791，召回一堆"企业共享文件夹界面"的图片识别片段
```

**✅ 正确做法**：拆成 3 条短的

| # | 检索词 | 命中 | 最高分 | 命中文档 |
|---|--------|------|--------|----------|
| 1 | `统一身份认证 同步学生 班级列表中无法查询到` | 7 | 0.791 | 统一身份认证 FAQ |
| 2 | `同步学生班级数据 class_info student_institution_relation 影响表` | 3 | **0.876** | 统一身份认证 FAQ |
| 3 | `统一身份认证 数据中台 同步学生 班级 缺失 排查` | 5 | 0.775 | 统一身份认证 FAQ / 数据同步自建问题 |

**同一条文档，拆词后 0.791 → 0.876**。这就是 Step 3 存在的意义。

### 8.4 Step 4-5 — 命中筛选与原文核对

| source_id | doc_title | kb | score | is_qa | 核对动作 |
|-----------|-----------|----|-------|-------|----------|
| **6487** | 统一身份认证 FAQ | 6 | **0.876** | false | `kb_get_document(6487)` → 读到"同步学生班级数据：school_info、college_info、grade_info、profe_info、class_info、student_institution_relation" |
| 6254 | 清空用户及组织机构数据-特殊操作谨慎处理 | 6 | 0.875 | false | 交叉印证表模型 |
| 724124 | 数据同步自建问题、删除不了问题 | 8 | 0.761 | false | 旁证 |
| — | 统一身份认证快速新增/同步学生未新增——数据集视图配置错误 | 6 | 0.728 | **true** | ⚠️ `is_qa=true` → **只当线索，不引用** |

**⚠️ 关键判定**：这个报错在 KB 里**没有专项文档**。命中的全是"表模型/影响表"类通用文档。
所以答复里必须写：**"KB 未检索到该报错的专项文档，以下为表模型层面的依据"** —— 不能把通用文档包装成官方解决方案。

### 8.5 Step 6-7 — 结论与回写

分析链条（把工单事实和知识点对上）：

```
报错"班级列表中无法查询到"
  → 校验发生在报文转实体之前 (saveStudent:207)
  → 查的是"班级列表" = 班级数据表
  → 知识库：同步学生班级数据影响 class_info 等表
  → 断点：中台侧班级主数据缺失 → 悬空引用 → 匹配失败 → 账号未创建
```

回写：

```
ticket_add_ticket_comment(
  ticketId=102,
  content="【学生同步失败排查结论】一、失败概况…六、附带现象…",   # 六段式，纯描述
  idempotencyKey="FB202610270001-sync-analysis-20261029-v1"     # 幂等，防重复日志
)
→ {"success":true,"logId":923,"duplicated":false}
```

**用户当时的要求**：「不要带任何学生信息，也不需要任何处理建议，就只需要描述」。
所以正文里**去掉了学号/姓名/身份证，连 82 个班级名也一并省略**（因为 73 个班只有 1 人失败，列班级名 ≈ 变相点名），只保留聚合计数。
→ **用户对"写什么"的偏好会改变产出结构，回写前先复述你要写的内容。**

### 8.6 Step 8 — 记工时（实际拟稿）

预检三条全跑：

```
calendar_is_workday("2026-10-29")                        → true      （10-31 是 false，要 isOvertime）
task_list_my_worklogs(10-26 ~ 11-03)                     → 只有 1 条：10-26 / 1h / 任务970 → 当天 0h，≤8h 通过
task_list_task_worklogs(taskId=993)                      → total=0，items=[] → 同日期无冲突
```

拟写入：

```
task_add_worklog(
  taskId=993, workDate="2026-10-29", hours=2,
  remark="数据同步失败排查：解析 10-29 同步失败导出（96 条/82 班），定位中台 edu_class_info 缺班级",
  isOvertime=false
)
```

⚠️ **副作用必须先报给用户**：这会把任务从「新建」推到「进行中」。若同时传 `progress`，还会覆盖任务进度并回填开始时间。

### 8.7 Step 9 — 完成工单（当时**不该**做）

```
ticket_update_ticket_status(ticketId=102, action="complete", comment="<根因/处置>")
```

**本例的判断：不做。** 根因虽然定位清楚，但**学校还没补录那 82 个班级，也没有回归验证** ——
此刻 complete 等于把未闭环的结论固化成"处理结论"写进任务日志。
→ **工单完成的前提是根因已闭环，不只是"分析清楚了"。**

### 8.8 这条链路上实际踩到的 5 个坑

| # | 坑 | 表现 | 处置 |
|---|-----|------|------|
| 1 | 工单描述只有一句话 | 拼不出检索词 | 找用户要导出文件；不要硬编 |
| 2 | 检索词太长 | 召回无关图片识别片段 | 拆成短查询，多轮搜 |
| 3 | `items[].id` 当 doc_id | `kb_get_document` 报"无权限访问此文档" | 用 `items[].source_id` |
| 4 | 命中的是通用文档 | 差点写成"官方方案" | 明说"KB 无专项文档" |
| 5 | 工单 `id`(102) vs `taskId`(993) | 工时会挂错任务 | 看清字段名 |
