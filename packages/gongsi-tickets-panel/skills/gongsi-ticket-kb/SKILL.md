## 0. 这个技能在做什么

```
用户提问 ──▶ ① 取工单详情 ──▶ ② 提炼检索词 ──▶ ③ kb_search 向量检索公司知识库
                                                                    │
        ⑦ 带出处的结论 ◀── ⑤ 核对原文 ◀── ④ 筛命中 ◀──────────────┘
                │
                ├──▶ ⑥ 回写工单说明 ──▶ ⑧ 记录工时 ──▶ ⑨ 完成工单

                └──▶ ⑩ 建单/转派   ⑪ 任务生命周期   ⑫ 知识沉淀   ⑬ 上传附件
```

## 1. 五条铁律

| # | 铁律 | 落地做法 |
|---|------|----------|
| 1 | **先取工单，再检索** | 没调 `ticket_get_ticket_detail` 就开口 = 答非所问。工单描述、附件截图、日志才是问题的真实载体 |
| 2 | **每个知识点都要能指回原文** | 引用时必须带 **文档标题**（`items[].doc_title`）。说不出出处的结论 = 你自己编的，删掉 |
| 3 | **`is_qa=true` 的片段不是原文** | 那是 AI 生成的问答，可能失真。**只能当线索**，必须 `kb_get_document` 找到原文段落才能引用 |
| 4 | **查不到就说查不到** | 知识库里没有就写"KB 未检索到"。**不许用常识补齐**，不许编表名 / 编报错 / 编根因 |
| 5 | **敏感信息默认脱敏** | 回写工单时避免写入身份证号、完整学生清单等 PII；用户指定"不要带学生信息"时严格执行 |
| 6 | **写操作先确认再执行** | 记工时 / 完成工单 / 回写工单都会**落到共享业务系统并产生副作用**。先把「拟写入的内容」摆出来给用户看，**用户点头才调工具**。不要"顺手"就写 |

## 2. 标准流程

### ⏱ 一条命令版（**默认走这个**）

```bash
node scripts/triage.mjs <工单号> --auto
```

一次输出：工单事实表 + 状态判读 + **它用过的检索式** + 知识库引用块。**一个进程跑完 ≈3s。**

`--auto` = 脚本自己从工单正文提炼检索式再检索。**优先用它**，原因见下。

下面 Step 1~5 是**同一件事的拆解说明**（想知道每步为什么这么做、或只要其中一步时才看）。
只要结果 → 跑上面那一条。

> **为什么 `--auto` 是默认**：检索式必须来自工单正文，所以"读工单 → 想检索词 → 检索"
> 天然要占**两个模型回合**——工单内容得先回到模型，模型才能决定检索词，然后才能发起检索。
> `--auto` 把这一步交给脚本，流程塌缩成一条命令，省掉中间那次推理。
> 自动提炼只是**初稿**：脚本会把工单事实表和用过的检索式打印在**同一份输出**里，
> 所以模型若觉得词不对，**补一轮 `--query` 时不需要重新读工单**。
>
> 提不出检索式时（工单正文太笼统、没有任何报错/表名/产品线索），
> `--auto` 会明说"自动提炼：没抽出可用检索式" —— 这时该向用户要证据，而不是硬编检索词。

### Step 1 — 锁定工单

**一条命令出全部工单事实**（推荐）：

```bash
node scripts/ticket-facts.mjs <工单号>      # 例：FB202610300001
```

输出 = 工单事实表（标题 / 描述 / 状态 / 类型 / 学校 / 处理人 / 附件 / **处理记录正文** /
关联任务 / 工时）+ **状态判读提示**。提示是脚本算出来的，**逐条看完再往下走**：

- 描述里有"已处理"但**人工处理记录 = 0** → 描述不是处理记录，闭环前必须向发起人核实"已处理"做了什么
- 状态是 `created` → 完成前要先 `action="start"`
- 平台 AI 分析已生成 → 那条 `ai` 日志只能当线索，**不能当原文引用**

工单号不明时用 `ticket_list_my_tickets(limit=40)`（**limit ≤ 40**，超了报 `-32006`），列出来给用户挑，别瞎猜。

### Step 2 — 把"问题"落到工单字段上

Step 1 已经把字段抽好了，这里只补两件事：

- **截图**：附件为 0 但描述里内嵌了图片（脚本已打印 URL）→ 下载后读图，看报错弹窗/堆栈
- **描述太笼统**（"同步有问题"）→ 结合附件、关联任务、处理记录反推真实问题，再进 Step 3

> ⚠️ **实测：不少工单的 description 只有一句话。** 例如 FB202610270001 的描述全文就是
> 「冯主任运维群反馈学生学校同步失败」，且 **0 附件**。这类工单**光靠工单字段拼不出检索词**。
> 此时把**用户在对话里提供的导出文件 / 日志 / 报错截图**当作"工单事实"补充来源 —— 先解析它，
> 拿到真实的报错文案、表名、代码位置、批次时间，再用这些去检索知识库。
> **没有补充材料时，不要硬编检索词**；直接告诉用户"工单描述过简，需要报错原文或导出数据才能定位"。

### Step 3 — 提炼检索词（这一步决定成败）

**不要拿整段描述去检索。** 抽出 3~5 个"检索式"，每个只含 1~2 个关键实体：
报错原文（去掉变量，如 `班级列表中无法查询到`）、表名/类名/接口名（`edu_class_info`）、
产品模块（`统一身份认证 同步学生`）、业务动作（`同步学生班级数据`）、工单类型（`数据排查`）。

**检索策略**：一轮里把 3 个检索式**并发**跑掉，不要一个一个来。

```bash
node scripts/kb-digest.mjs --query "获取部门信息 部门管理" --query "单位管理 单位类别" --query "新增服务 归属部门"
```

脚本会：**并发** kb_search → 按 score 过滤 →
按文档去重 → **并发**逐分片拉原文 → 输出「可直接粘进【知识库依据】的表格」+「带出处的原文引用块」。
命中块上已标好 `doc_title / kb_id / source_id / chunk_index / score / 是否 is_qa`。

> **检索轮次上限 = 2 轮。** 第 2 轮还不覆盖，就按铁律 4 写"KB 未检索到" ——
> 不要继续加检索式硬凑，那只是在烧时间（每个检索式 ≈1.7s）。

> ⚠️ **三个提速点**（实测数据，逐环节耗时见 `references/tool-map.md` §12）：
> ① **已知库就用 `--kb` 收窄**（全库 ≈1.76s → 单库 ≈1.2s）；库号见 `references/kb-map.md` §6。
> ② **别调大 `--top-k`**：响应体大小取决于**命中的分片内容**（图片识别块可以很大），不是条数决定的
>    —— 同一查询 `top_k=5` → 12KB ✅，`top_k=8/10` → 69KB ❌ 撞 64KB 预算要重试。**要更多召回就收窄 `--kb`。**
> ③ **别分两个脚本跑**：每个进程都要重付 TLS + MCP `initialize`（≈0.22s）＋两次 shell 往返
>    —— **用 `scripts/triage.mjs` 一个进程跑完「工单事实 + 检索」。**

> 脚本内置 **top_k 自动收敛 + 服务端超时重试**（客户端 8s 先放弃 → 收窄重试 → 连续超时则放弃该式）。
> **看到「超 64KB 通道预算」或「服务端执行超时」提示，就说明这一轮已自动降级过了** ——
> 别把它当成"KB 里没有"，也别再手动重试同一组词；直接读剩下的命中块，
> 确实不够就按铁律 4 写"KB 未检索到"。

### Step 4 — 检索结果怎么读

`kb_search` 每条命中里，**脚本已经打印**：`doc_title`（引用写这个）、`source_id`（文档ID）、
`chunk_index`、`score`、`is_qa`（`true` = AI 生成问答，见铁律 3）。

**脚本没打印、但你判断时要知道的 4 个字段**：

| 字段 | 含义 |
|------|------|
| `id` | **分片 ID，不是文档 ID** —— 拿它读文档会报"无权限访问此文档"，要用 `source_id` |
| `chunk_type` | `parent` = 多片段合并的大块；`paragraph` = 段落 |
| `contentTruncated` | `true` = 片段被截断，**不能当完整结论** |
| `metadata._hit_child` | 父分片里真正命中的那段（脚本优先用它） |

### Step 5 — 核对原文（不可跳过）

**脚本已经替你核对过了**：kb-digest 自动对每个命中分片调 `kb_get_context` 拉了原文段落。
**你剩下要做的判断只有一件：命中的内容是否覆盖了用户问的那个问题。**

- `is_qa=true` → 脚本已标「仅线索」，**不可直接引用**
- 知识库之间说法冲突 → 以**产品FAQ文档（kb_id=6）**为准，其他库作为补充
- 还要读全文时：`kb_get_document(doc_id = source_id, max_chars = 15000)`（超长会返回 truncated=true）

> ⚠️ **命中不等于覆盖。** 检索到的可能只是**表模型 / 影响表 / 清空数据**这类通用文档，
> 而**没有**该具体报错的专项条目 —— 例如查「班级列表中无法查询到」时，KB 命中的是
> 《统一身份认证 FAQ》的"同步影响表"和《清空用户及组织机构数据》，**并没有**讲这个报错的专文。
> 这时必须写清楚：**"KB 未检索到该报错的专项文档，以下为表模型层面的依据"**，
> 不要把通用文档包装成"官方解决方案"。

### Step 6 — 组织答复（见第 3 节模板）

> ⚠️ **Step 7~13 是写操作**（回写工单 / 记工时 / 完成工单 / 建单 / 转派 / 任务流转 / 知识沉淀 / 传附件），
> 细则与参数见 `references/write-ops.md`。**必须先读它**，且**必须先向用户展示拟写入内容、得到确认才执行**。

```markdown
## 结论

| 知识点 | 出处文档 | 原文要点 |
|---|---|---|

把工单事实和知识点对上：
报错原文含义 → 校验发生在哪一步 → 涉及哪些表 → 这些表由谁同步 → 所以断点在哪
```

- 用户要"只要描述不要建议"时，去掉【建议动作】那一节

## 5. 高频坑速记（最容易出错的 6 条，细则见 references/tool-map.md §11）

| # | 坑 | 一句话对策 |
|---|-----|-----------|
| 1 | 分片 `items[].id` 当文档 ID 用 | 传 `items[].source_id`，否则报"无权限访问此文档" |
| 2 | `is_qa=true` 的 AI 生成问答当原文引用 | 只当线索，必须 `kb_get_document` / `kb_get_context` 找到原文段落才能引用 |
| 3 | 工单 `id` 与 `taskId` 混淆 | 工时挂 `taskId`（关联任务），不是 `id`（工单）—— 两个不同的数 |
| 4 | 命中的是通用文档 | 明说"KB 未检索到该报错的专项文档"，不要包装成"官方解决方案" |
| 5 | 描述写"已处理"就以为已闭环 | 描述**不是**处理记录；看 `ticketStatus` / 任务状态 / 工时 / `logs` 有没有人工记录 |
| 6 | 检索词一整句丢进 kb_search | 拆成"报错片段""表名""动作"多轮短查询，分数能从 0.79 提到 0.88 |
